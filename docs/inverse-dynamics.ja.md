# 逆動力学 —— analysis-by-synthesis の土台 (M4)

> `import { makeRig, simulate, estimateControl } from 'xpbd-body/inverse'`

ネットに転がっている2D映像が見せてくれるのは「**関節がどこへ行ったか**」だけだ。そこに写っていないのは、それを起こした**制御** —— 筋張力・関節トルク・タイミング・協調。だが体の物理的制約(可動域・質量・慣性・筋の引き方)は十分に強い prior なので、**位置から制御を逆算できる**。これが古典的な逆動力学であり、[keiko-engine](https://github.com/opaopa6969/keiko-engine) の稽古ループが「動きの記述子＝生の2D位置ではなく、体モデルを通して推定した制御」を採るために必要な土台。

xpbd-body はもともと問題の半分を持っていた。能動ラグドール —— コンプライアンスを持つ `Motor`(筋肉)が、質量と重力を持つ本物のチェーンを駆動する —— これ自体が**前向きモデル**(制御→軌道)そのものだ。M4 は、その上に推定ループが必要とする2つを足す。

```
                 ┌──────────── 前向きモデル(既にあった) ────────────┐
   制御    ───► │  Motor目標 → XPBDサブステップ → 質量・重力・接触  │ ───► 軌道
                 └────────────────────────────────────────────────┘
                                          ▲                    │
    estimateControl: 推測を直す ──────────┘      差を見る ◄────┘   観測された軌道
```

## API

### `snapshot(world)` / `restore(world, snap)` —— 巻き戻し

全 body の `p / q / v / w` と、**モーターの制御状態**(`rest` 目標 + `compliance`)を plain data でダンプする。推定ループはこれが無いと成立しない —— 制御Aを試し、巻き戻し、ビット単位で同一の初期状態から制御Bを試す、が必須だから。snapshot は不活性なので、いつまで持っていてもよい。

### `makeRig(opts)` —— カラダと、その prior

world・駆動するボーン・そして逆問題を解ける形にするための2つの prior: **`rom`**(ボーンごとの関節可動域、Euler XYZ。sotai-engine の ROM がそのまま入る)と **`maxTorque`**(ボーンごとの持続筋張力の上限)。加えて `rig.initial` —— 各推定トライアルが出発する静止状態の snapshot。

### `simulate(rig, controlTrajectory, dt, steps)` → `poseTrajectory` —— 前向きモデル *(issue #2)*

pure。**副作用なし**: 入口で world を snapshot し、出口で restore するので、呼び出し側の走っているシミュレーションは一切汚れない。**決定論**: 同じ初期状態＋同じ制御 → バイト同一の出力。既存の逐次 `world.step(dt)` API はそのまま —— リアルタイム用途はここを通らない。

制御フレームは `{ pose: { bone: [x, y, z] }, compliance?: { bone: number } }` —— motion-engine のポーズと同じ Euler XYZ。短い軌道は最後のフレームを保持する。出力フレームは `rel`(ボーンのローカル回転＝レンダラが適用するもの)・`pos`・`torque`(その瞬間に筋肉が引いている力)を持つ。

### `estimateControl(rig, observed, opts)` → `{ control, residual, feasible }` *(issue #3)*

制御を仮定し、前向きに回し、ズレを見て、仮定を直す。**勾配なし**(シミュレータは接触入りのブラックボックスで、綺麗な微分は無い)、そして**決定論**(seed付きPRNG。`Math.random` はこの repo のどこにも無い)。

- **パラメータ化**: 制御はフレームごとの自由な目標ではなく、ボーンごとの少数の**knot**(Euler三つ組。フレーム間は線形補間)。探索空間が数千次元から数十次元に潰れるうえ、これ自体が滑らかさの prior になる —— 筋肉はテレポートしない。`knots` がバイアス/バリアンスのつまみ。
- **初期化**: 探索は**観測そのもの**から始める。見えているポーズは、筋肉が狙っていたポーズの既に良い推測だ —— 両者の差は「垂れ(sag)」であり、探索が見つけるべきものはまさにそれ。ここが optimizer 本体より効く。
- **目的関数**: 観測との関節角の重み付き二乗和(＋オプションで位置誤差)＋**制御の曲率に対する平滑化正則化**。
- **optimizer**: `'coord'`(座標降下/パターン探索。ステップを縮めていく。既定であり、ここでは精度も上)か `'cem'`(交差エントロピー法、seed付き。地形が荒いときに有用)。CEM で効くのは `sigma0` —— 良い初期値から始めるので、サンプリング雲が広いといつまでも悪い制御ばかり引く。

## 実現可能性 —— 観測が「嘘」でありうる3つの経路

`feasible: false` には `violations[]` が付き、どの関節がどれだけ超えたかを名指しする。

| prong | 何を捕まえるか |
|---|---|
| **`rom`** | 観測された関節角が可動域の外。肘が逆に曲がるのは「難しい制御」ではなく、不可能。 |
| **`torque`** | 再現するのに、モーターの上限を超える**持続的**な筋の引きが要る。 |
| **`residual`** | そもそもカラダが到達できない: 見つかった最良の制御でも、まるで届かない。 |

3つ目が曲者で、**「自重で崩壊する姿勢」はここに出る**。弱い筋肉は*大きなトルクを出せない* —— だから垂れているカラダでは、トルクの prong は**構造上**静かなままだ。正体を暴くのは「どの制御も観測を再現できない」という事実のほう。トルク上限だけを見ていると、重力崩壊はすり抜ける。(これは実装中に足をすくわれた。テスト #25。)

持続トルクは軌道の**中央値**であって、ピークではない。モーター目標が階段状に変わると数フレームだけトルクが跳ねる —— それはシミュレータの過渡応答であってカラダの努力ではないし、ピークに上限を掛けたら「制御がどれだけ乱暴に書かれたか」を測っているだけになる。

トルクはモーターを「コンプライアンスを持つねじりバネ」として読む: `τ = 追従誤差 / compliance`。サブステップ非依存で、定常状態では重力が要求しているトルクに一致する —— それこそが狙い。単位は**エンジン単位**でありニュートンメートルではない: このカラダの慣性は球近似で、compliance も人体に対して較正されていない。だから `DEFAULT_MAX_TORQUE` は意図的に緩い(通常の動きは、柔らかい筋肉で ~10、非常に硬い筋肉で ~600 程度に落ちる)。rig ごとに締めれば、同じ機構が**弱いカラダ**をモデルする。

## 限界 —— 数字を信じる前にここを読む

**この逆問題は不良設定(ill-posed)である。** これは工夫で消せる注意書きではなく、問題そのものの形だ。

- **同じ動きを生む制御は複数ある。** ポーズをぴったり狙う硬い筋肉と、はるか先を狙う緩い筋肉が、同じ場所に落ち着きうる。`estimateControl` は「**その**制御」を返さない。**1つの**制御 —— 適合する解の族の中から、残差と平滑化正則化が選び出した1つ —— を返す。それを声に出して言うために `unique: false` を返している。`smooth` を変えれば、別の、同じくらい妥当な答えが出る。
- **接触力は観測できない。** 卓に寄りかかっていれば、仕事の一部は卓がやっている。姿勢の軌道はそれがどれだけかを何も語らない。推定器は卓の支えを筋肉のせいにし、残差からは見えない形で間違った制御を返す。
- **単眼の観測に奥行きは無い。** 2D動画を3D関節角に持ち上げた時点で、奥行きは*推測*だ。下流はそれを丸ごと相続する。xpbd-body は3D姿勢軌道を受け取るだけで、それがどこから来たかを問わない —— 奥行きの曖昧性は上流にあり、無視しても消えない。
- **knot が復元可能なものの上限を決める。** knot で表現できないより細かい構造を持つ制御は、平滑化されて消える。意図した prior だが、prior であることに変わりはない。

残差を使え。残差の大きい制御は「真の制御の推定として下手」なのではなく、「**このカラダにはそれはできない**」という宣言だ。

## 実測

Node 20、1コア。

| | 上半身フル(13 body) | 3ボーンの腕 |
|---|---|---|
| 前向き `simulate`、2秒 @60Hz、substeps=20 | 43 ms | 9.5 ms |
| …substeps=8 | 14.5 ms | 3.6 ms |
| …substeps=4 | 8.8 ms | 2.4 ms |

つまみは substeps。20 がリアルタイムの既定で、推定ループは大抵 8 まで落とせる —— 3倍安くなって、残差は小数第3位に留まる。

**合成往復検証**(3ボーンの腕、1秒、substeps=8、knots=3、座標降下5スイープ) —— 既知の制御から軌道を作り、制御を捨て、推定で取り戻す:

- 関節角の残差: **rms 0.0029 rad / max 0.0074 rad**(0.17° / 0.42°)
- **真の制御**に対する誤差: **rms 0.0029 rad / max 0.0074 rad**
- 前向きシミュレーション 178回、計 ~400 ms
- CEM(8世代 × 16サンプル、seed付き): rms 0.0043 rad、129回

制御空間の誤差が姿勢残差と同じオーダーに収まったのは*良いケース*であって一般則ではない。この観測は**このカラダ自身が生成した**ものだから、動きを再現する制御は、それを作った制御の近くにいる。実写に対しては、姿勢残差は小さいままでも、制御の誤差を縛るのは上に挙げた prior だけになる。
